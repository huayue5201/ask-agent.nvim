1. DESIGN                                                   *ask-agent-design*

Agents that run outside Neovim only see what is on disk. This plugin sends the
question *and* the thing you are looking at: cwd, tab, `file:line`, visual
selection, unsaved state. Delivery is a socket or a command line, so it works
with any agent that can receive text.

2. SETUP                                                     *ask-agent-setup*

>lua
require("ask_agent").setup({
  matching = "exact",            -- "exact" | "related" | "single"
  picker = "map",                -- "map" | "list"
  show_stale = true,             -- list exited instances too, marked "not running"
  spinner = { "⠋", "⠙", "⠹" },      -- frames for the busy icon (default: braille)
  tick = 90,                     -- animation interval in ms (default 90)
  state_interval = 2000,         -- state polling interval in ms (default 2000)
  state_notify = true,           -- notify on finished/blocked agents (default true)
  persist = true,                -- keep tasks/unread marks in the journal (default true)
  default = "pi",                -- default backend id
  extra = {},                    -- backends registered at setup time
  icons = {                      -- every glyph: flat key = an agent icon,
    pi = "π",                    -- "ui" group = the interface (see *ask-agent-icons*)
    ui = { state = { done = "✓" }, spinner = { "⠋", "⠙" } },
  },
  icon_colors = {},              -- per-agent brand colors (hex)
  aliases = { file = vim.fn.stdpath("cache") .. "/ask-agent/aliases.json" },
  bridge = { dir = vim.fn.stdpath("cache") .. "/pi-ctx" },  -- false disables
})
<

                                                 *ask-agent-icons*
Icons and marks
Everything the plugin draws is configured through the `icons` option and defined
in `lua/ask_agent/icons.lua`:

  flat key       an agent icon, keyed by backend or instance id; `fallback` is
                 used for unknown agents
  ui.header      dashboard winbar and notification prefix
  ui.state       blocked done error working idle unknown gone
  ui.task        queued done error (dashboard tree)
  ui.tree        collapsed expanded leaf
  ui.spinner     busy frames; the list replaces the default frames entirely

  >lua
  require("ask_agent").setup({
    icons = { claude = "", ui = { state = { blocked = "!" } } },
    icon_colors = { claude = "#d97757" },
  })
  <
Only the keys you pass change; everything else keeps its default. A top-level
`spinner` option still wins over `ui.spinner`.

3. COMMANDS                                               *ask-agent-commands*

                                                        *:AskAgent*
:AskAgent [text]        Ask the current backend; the cursor position is the
                        anchor. Without [text] the ask window opens.

                                                  *:AskAgentVisual*
:AskAgentVisual         Ask with the visual selection as anchor.

                                                  *:AskAgentPi*
:AskAgentPi             Ask the `pi` backend explicitly.

                                                  *:AskAgentBackend*
:AskAgentBackend [id]   Switch the default backend, or pick one.

                                                  *:AskAgentPicker*
:AskAgentPicker [mode]  Choose how multiple candidates are presented.

                                                  *:AskAgentTarget*
:AskAgentTarget [id]    Pin the target instance (skip matching); `!` clears.

                                                  *:AskAgentAlias*
:AskAgentAlias          Name an instance; names show up in lists, prompts and
                        notifications. `!` clears a name.

                                                  *:AskAgentDashboard*
:AskAgentDashboard      Open the sidebar: agents as a tree, each agent's queued
                        and sent tasks below it. `<CR>` jumps (agent window /
                        task anchor), `s` send, `S` flush its queued questions,
                        `a` acknowledge, `d` delete a queued task or dismiss a
                        dead agent, `<Tab>` fold,
                        `?` key help, `r` poll now, `q` close.

                                                  *:AskAgentBatch*
:AskAgentBatch          Queue a question at the cursor instead of sending it.

                                                  *:AskAgentBatchVisual*
:AskAgentBatchVisual    Queue a question anchored to the visual selection.

                                                  *:AskAgentBatchSend*
:AskAgentBatchSend [ids]
                        Send queued questions, one message each. Routed entries
                        go to their own agent; the unrouted rest shares one
                        target picker. `ids` picks a subset (`3`, `3,5-7`);
                        without it every entry is sent. Successful entries leave
                        the queue; failed ones stay for a retry.

                                                  *:AskAgentBatchRoute*
:AskAgentBatchRoute [ids]
                        Route queued questions to one target (`ids` as above;
                        without it every entry). The marker then reads
                        `[3→name]` in that instance's color, and a batch send
                        delivers the entry there. `!` clears the route again.

                                                  *:AskAgentBatchList*
:AskAgentBatchList      List queued questions; choose send now, route to an
                        agent, jump to code, edit or delete.

                                                  *:AskAgentBatchDelete*
:AskAgentBatchDelete    Delete the queued question(s) on the cursor line (asks
                        which one when several sit there).

                                                  *:AskAgentBatchUndo*
:AskAgentBatchUndo      Undo the last delete or clear: put the entries back with
                        their markers. Entries whose buffer was wiped meanwhile
                        are skipped.

                                                  *:AskAgentBatchClear*
:AskAgentBatchClear     Drop every queued question and its marker (undoable).

4. KEYMAPS                                                 *ask-agent-keymaps*

The plugin installs no keymaps: commands are the public interface, mappings belong
to your config. Example:

>lua
vim.keymap.set({ "n", "v" }, "<leader>aq", function()
  require("ask_agent").ask({ visual = vim.fn.mode() ~= "n" })
end, { desc = "Ask agent" })
vim.keymap.set({ "n", "v" }, "<leader>ab", function()
  require("ask_agent").batch_ask({ visual = vim.fn.mode() ~= "n" })
end, { desc = "Ask agent: queue" })
vim.keymap.set("n", "<leader>aB", "<cmd>AskAgentBatchSend<cr>", { desc = "Ask agent: send queue" })
vim.keymap.set("n", "<leader>ai", "<cmd>AskAgentAlias<cr>", { desc = "Ask agent: alias" })
<

In the ask window: `<C-s>` sends, `<Esc>`/`<C-c>` cancels, `<CR>` inserts a newline.
In the map: a letter picks that pane, `<Tab>` switches to the list.
In the list: a number (`<M-a>`… past 9) picks where the implementation offers
those; `<Tab>` returns to the map unless the implementation already maps `<Tab>`.

5. PICKERS                                                 *ask-agent-pickers*

`map` draws the split layout of your terminal multiplexer and puts a bold letter
in every pane that hosts an agent. All windows of the session are stacked top to
bottom (the window nvim lives in comes first), so an agent running in another
window still gets a cell. A zoomed window is drawn as the single pane it shows.
A pane covered by a floating window still gets its letter — placed on a visible
cell of that same pane, so nothing is painted over the floating window. Blocks
are laid out compactly (no gaps) and the map is centered on screen.

`list` is a plain list of every instance, including ones in other tabs and
windows, shown through `vim.ui.select` — so it is whatever your config provides
(dropbar, telescope, fzf-lua, snacks, …), with no hard dependency. Each entry
shows the instance glyph in its own stable color, the name, and the cwd. Float
menus are centered rather than attached to the cursor.

Every entry starts with the agent's state, re-probed when the picker opens:

  ●  idle — the agent is free, the question is handled right away
  ◐  working (rotating spinner when the picker animates) — a turn is running; the
     question is still delivered now
     (pi queues it as a follow-up and runs it after the current one), and a
     notice tells you so
  ⚠  blocked — the agent is waiting for you (permission, a question, auth); a
     send would sit in its input unread
  ✓  done — the last turn finished and nobody looked at it yet
  ✗  error — the turn ended in an error
  ○  not running — process exited, socket missing, pane gone/dead, or the pane
     fell back to a shell

Busy rows animate only if the picker implementation supports it. ask-agent passes
`tick` (default 90 ms, see the `tick` setup option) in the `vim.ui.select` opts and
reads `format_item(item, frame)`; that is the contract `lib/menu.lua` honours
(re-render every tick while waiting for a key).
Other implementations (telescope, fzf-lua, snacks, dropbar) ignore the key and show
the first spinner frame as a static icon. The frames themselves come from the
`spinner` setup option (default: a 10-frame braille spinner); point it at whatever
spinner your picker uses -- e.g. `require("lib.menu").frames` -- so busy rows look
the same in the list and in the map. The map is callback-driven instead of
blocking, so it animates with a uv timer that repaints busy cells and is stopped
when the map closes (no option to set).

The probe may add a short detail next to the dot (the pane's command, "busy",
"process exited", ...). `pi` reports busy via the `busy` field its extension
rewrites on agent_start/agent_settled; other backends may not report it.

Exited instances reported by the backend (`stale_targets()`) are listed at the
end, marked `○ … (exited)`, so a vanished agent is visible instead of absent.
They can never be chosen: picking one only warns and nothing is sent. Disable
with `show_stale = false`. The map shows running instances only.

Without a layout adapter, or when fewer than two candidates can be located on
screen, the map silently falls back to the list.

6. BACKENDS                                               *ask-agent-backends*

A backend is a table (see `lua/ask_agent/backends/init.lua`):

  id        unique id, e.g. "pi"
  label     shown in prompts
  targets() live instances
  send(target, text) -> ok, err?
  icon      optional glyph
  available() optional: ok, reason?
  status()    optional: ok, reason?
  probe(target) optional: { running, busy?, detail? }  live check for the picker
  stale_targets() optional: table[]             recently exited instances,
                                                shown in the list as "○ not running"

A target is one instance:

  id        stable within its lifetime (pid, socket path, pane id …)
  label     human label, e.g. "pid 12345"
  cwd       project directory (used for matching)
  ts        start time (ordering, alias staleness, color)
  sock      optional delivery endpoint
  rex       optional { session, block }: where it lives, as the rex adapter reads it
  layout    optional: same, in the shape another layout adapter expects
  icon      optional per-instance glyph
  avoid     optional warning to show before sending

Porting to another agent, in five lines: if it runs in a tmux pane, the bundled
factory is all you need (no new file, no plugin change):

  local generic = require("ask_agent.backends.generic")
  require("ask_agent").setup({ extra = {
    generic.tmux({ id = "claude", label = "Claude Code",
                   panes = generic.tmux_panes_by_cmd("claude") }),
  } })

`generic.tmux(opts)` implements `targets()` from the pane list, `send()` (tmux
load-buffer -> paste-buffer -> keys_after, so multi-line text does not turn into
several Enters and quoting is not involved) and `probe()` (pane alive, not dead,
still running the agent). Options: `panes`, `keys_after` (default "Enter"),
`icon`, `busy`. The picker, status dots, batch queue, aliases and the map all come
from the core. Other options for `panes`:
  generic.tmux_panes(match)      all panes as { id, command, cwd, title }
  generic.tmux_panes_by_cmd(pat) filter by pane_current_command

Busy is the one thing tmux cannot report. The recommended route is the agent's own
hooks writing a marker file, read by `generic.state_file(dir, opts)`:

  busy = generic.state_file("~/.cache/ask-agent/claude", { field = "cwd" })

The marker is `<dir>/<slug(key)>.json` holding `{"busy": true}`;
`generic.slug()` is the same escaping a shell hook can reproduce. Missing or
invalid markers mean "unknown" (never blocks sending), and a marker older than
`opts.ttl` (default 3600s) also means unknown, so a crashed session does not look
busy forever. Screen scraping (capture-pane) is possible by writing your own
`busy` function, but it breaks with UI changes, so it is not built in.

Claude Code is bundled: `backends/claude.lua` builds the tmux backend above with
`id = "claude"`, `label = "Claude Code"` and the hook marker directory
`$XDG_CACHE_HOME/ask-agent/claude`. Register it with

  require("ask_agent").setup({ extra = { require("ask_agent.backends.claude").new() } })

and switch with `:AskAgentBackend claude`. `new()` accepts
`id, label, command, command_pattern, state_dir, field, ttl, keys_after`.
The matching hook script is `extensions/claude-ask-agent-state.sh`; install it as
`~/.claude/ask-agent-state.sh` and add these hooks to `~/.claude/settings.json`:

  UserPromptSubmit -> ask-agent-state.sh busy
  Stop             -> ask-agent-state.sh idle
  SessionStart     -> ask-agent-state.sh idle
  SessionEnd       -> ask-agent-state.sh idle

For non-tmux transports (unix socket, HTTP, file drop, ACP) write a module
returning the table above and register it with `setup({ extra = { mod } })` or
`require("ask_agent.backends").register(mod)`. `tests/backends.lua` in the repo is
a reference: run it from the repo root with
`nvim --headless --clean -l tests/backends.lua` and read how little a
hand-written backend needs.

Individual instances are told apart by a stable color (hash of `id:ts`) and by
an optional name; see |ask-agent-aliases|.

7. INSTANCE NAMES                                   *ask-agent-aliases*

Names are stored in a JSON file (default under `stdpath("cache")`), keyed by
instance id and stamped with its start time, so a recycled pid never inherits an
old name. Set or clear them with |:AskAgentAlias|.

8. LAYOUT ADAPTERS                                   *ask-agent-layouts*

The map needs to know where each instance sits, which is multiplexer-specific:

  id            unique id, e.g. "zellij"
  available()   -> ok, reason?
  window()      -> win, data          "the window nvim itself lives in"
  windows()     optional -> list      every window of the session, each
                                      { window = win, panes = { ... }, current? };
                                      use it to include agents in other windows
  panes(win)    -> { { id, rect = { x, y, w, h }, kind = "tiled"|"float" }, ... }
                  rect is normalised 0..1, y from the top, later entries paint on top
  match(target) -> pane id|nil        which pane hosts this instance
  cursor()      optional -> pane id   where nvim is focused
  labels(data)  optional -> pane id -> label

Register with `ask.register_layout(mod)`, choose a default with
`setup({ layout = "zellij" })`, or read/set it with `ask.layout()`.

Shipped: `rex` (auto-registered, `lua/ask_agent/layouts/rex.lua`) and a tmux
factory — `require("ask_agent").register_layout(require("ask_agent.layouts.generic").tmux())`.

9. RPC BRIDGE                                         *ask-agent-bridge*

`setup()` starts a Neovim RPC socket and writes a registration file so an agent
can pull live context (unsaved buffers, diagnostics, quickfix) back out:

>sh
nvim --server <sock> --remote-expr \
  'v:lua.require("ask_agent.bridge").handle("<base64(json)>")'
<

Actions: `state`, `buffer`, `diagnostics`, `quickfix`, `list`, `project`,
`agents` (optional `state` filter), `ask` (`{text, backend?, target?}`),
`task` (`{key}`) and `status`. The last four expose
the agent control plane over the same socket, so a terminal agent can list what
is blocked and read the outcome.
Handlers return JSON and never throw. Register extra actions from your config:

>lua
require("ask_agent.bridge").extend("project", function(req)
  return { ok = true, text = my_summary(req.root) }
end)
<

`project` has no built-in implementation: it depends on the host config's
project tooling.

MCP: `bin/ask-agent-mcp` speaks MCP over stdio and forwards the same actions, so
clients that only understand MCP get `agents`/`ask`/`task`/`status` as
tools. Point the client at the script; it finds the nvim instance
working in the current directory (override with `$ASK_AGENT_SOCK`).

10. AGENT STATUS                                            *ask-agent-status*

`ask_agent.state` is the single truth about every instance: the picker, the
dashboard, the statusline and other plugins all read from it, so they cannot
disagree. It polls every `state_interval` ms (default 2000, `state_notify =
false` silences blocked/done/error/exit notifications).

Sources, strongest first:

  rex program status  rex reports each block's OSC 7501 status (`working`,
                      `blocked` with a kind, `done`, `error`, plus `msg` and
                      `progress`). Used for targets carrying
                      `rex = { session, block }`, and streamed through
                      `rex events -s SESSION --json` so changes arrive in
                      milliseconds instead of at the next poll.
  backend probe       `busy` means working, a hook marker may also carry
                      `{state, kind, msg, progress}`; no probe means unknown;
                      `running = false` means gone.
  our send log        a turn that ends after we sent something becomes `done`
                      with `unread = true` (that survives a source that only
                      knows idle, until you acknowledge it).

`rec.source` says which one produced the state: `rex`, `probe`, or `heuristic`
(the last one only knows idle, so the sidebar labels the turn `inferred`).

States: `idle`, `working`, `blocked` (kind: permission | question | auth),
`done`, `error`, `unknown`, `gone`. Every transition into `blocked` is reported;
`done` and `error` are throttled to one per 30 s per instance, and `done` is
silent while its local terminal is the current window. They stay in the dashboard
and count in the statusline until acknowledged. An agent that exits while working
or blocked is reported too. Nothing is accepted or rejected automatically: the
agent CLI stays the place where work is approved.

>lua
local ask = require("ask_agent")
ask.agents({ state = "blocked" })          -- what needs me now, most urgent first
ask.on("done", function(rec)
  local c = rec.dispatch and rec.dispatch.correlation
  if c and c.plugin == "todo2" then require("todo2").complete(c.key) end
end)
ask.wait("pi:91841", "done", 600000, function(rec) ... end)
ask.statusline()                             -- "⚠1 ✓2 ◐3", empty when idle
<

A blocked instance is only reported: the sidebar and statusline show it, and
`<CR>` jumps to its terminal. It is answered in that terminal, not from Neovim.
Tasks and unread marks are journaled to
`<cache>/ask-agent/journal.json` (1 s debounce, week-old tasks dropped, disable
with `persist = false`), so a restart keeps pending work visible.

`rec.dispatch = { ts, correlation }` records when we last sent and the
opaque correlation table given to `ask.send(text, { correlation = { plugin, key } })`;
it comes back with every event for that instance. Every send is also appended to
`rec.tasks` (newest first, the last 20): `{ text, ts, status, correlation, anchor }`
with `status` = `running` / `done` / `error`.

11. DASHBOARD                                        *ask-agent-dashboard*

|:AskAgentDashboard| opens a sidebar tree on the right (40 columns; pass
`{ pos = "left", width = 30 }` to `ask.dashboard()` to move or resize it). Top
level: agent instances, most urgent first. Children: that agent's tasks — questions still queued for it (`◐`) and
turns already sent (spinner running, `✓` done, `✗` failed). Agent glyphs: `●`
idle, spinner working, `⚠` blocked, `✓` done, `✗` error, `◌` unknown, `○` exited.

`<CR>` on an agent brings its window to the front; on a task it jumps to the code
anchor the task was written at. `s` sends, `S` flushes every queued question
routed to that agent, `a` acknowledges, `d` deletes a
queued task or dismisses a dead agent, `<Tab>` folds its tasks, `?` opens the key
help float, `r` polls now, `q` closes. The view is event-driven (state + queue notifications) and keeps the
cursor where it was; the spinner is the only timer and only runs while a turn is
in progress.

Which terminal or multiplexer shows an agent is user-specific, so jumping goes
through an adapter:

>lua
ask.register_jump({
  id = "herdr",
  priority = 10,                  -- higher wins when several adapters match
  can = function(target) return target.pane ~= nil end,
  focus = function(target) vim.system({ "herdr", "focus", target.pane }) end,
})
<

rex (`target.rex`) and tmux (`target.pane`) ship built in. The first matching
adapter (highest `priority`) handles the jump. The rex adapter runs two steps,
because a Rex app keeps showing whichever session it had selected: `rex do
session.select session_id=...` (the app-side action, `REX_CLIENT` picks the app
when several are connected) and then `rex block focus <block> -s <session>`,
which also activates the block's window. Failures become warnings.

12. BATCH QUESTIONS                                         *ask-agent-batch*

Queue questions while browsing instead of sending them immediately. Each queued
entry keeps the anchor captured at the time (cwd, file, line, selection), is
drawn in the source buffer as a `»` sign plus end-of-line virtual text, and
follows buffer edits through its extmark. |:AskAgentBatchSend| sends every entry
as its own message; |:AskAgentBatchSend| `3,5-7` sends only those.

|:AskAgentBatchRoute| routes entries to a specific agent instance of the current
backend (|:AskAgentBackend| switches backends); the marker shows `[3→name]` in that
instance's color, so one queue can be split across several running agents: a send
groups by route, routed entries go to their own agent and the unrouted rest shares
one picker.

In the ask window: `<C-s>` queues the question, `<Esc>`/`<C-c>` cancels.
Use |:AskAgentBatchList| to jump to an entry's code, edit its text or delete it,
or |:AskAgentBatchDelete| to drop the entry under the cursor. Every delete and
|:AskAgentBatchClear| can be reversed with |:AskAgentBatchUndo| (the last 20
operations are kept in memory, as is the queue itself — the current session
only).

13. API                                                    *ask-agent-api*

>lua
local ask = require("ask_agent")
ask.setup(opts)
ask.ask({ visual = true })
ask.batch_ask({ visual = true })
ask.batch_send({ ids = "3,5-7" }) / ask.batch_route(ids, opts)
ask.batch_list() / ask.batch_clear() / ask.batch_count()
ask.send(text, opts)                    -- { backend, target, correlation, anchor }
ask.agents({ state = "blocked" })       -- instances, most urgent first
ask.on(event, fn)                       -- state | update | done | blocked | error
ask.wait(key, want, ms, cb)             -- one-shot wait; cb(nil) on timeout
ask.statusline() / ask.dashboard(opts)  -- sidebar; { pos = "right", width = 40 }
ask.goto_anchor(a)                      -- jump to a captured anchor
ask.use("pi") / ask.current()
ask.list() / ask.targets("pi")
ask.pin(id) / ask.pinned()
ask.alias(target, name) / ask.alias_of(target)
ask.picker("map"|"list")
ask.register(backend)
ask.register_layout(adapter) / ask.layout(id)
ask.register_jump(adapter)              -- bring an agent's window to the front
ask.generic  -- tmux backend factory; also tmux_panes(match),
             -- tmux_panes_by_cmd(pat), state_file(dir, opts), slug(s)
<
